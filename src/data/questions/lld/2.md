## Question
Design an in-process rate limiter class exposing `allow(client_id) -> bool` that permits at most N requests per client per rolling window of T seconds, safe under concurrent calls.

## Requirements
- Per-client limits, isolated from each other.
- A rolling window (not a fixed-bucket reset that lets 2N requests through across a boundary).
- Thread-safe under concurrent `allow()` calls for the same client.
- Bounded memory even for clients that stop sending requests.

## Hint
A fixed window (`count resets every T seconds`) is the simplest thing that could possibly work -- and the simplest thing that's provably wrong for "rolling window". Think about what state you need to actually be rolling.

## Approach
Sliding-window log per client: store each client's recent request timestamps in a deque. On `allow()`, pop timestamps older than `now - T` off the front, then admit iff the remaining count is `< N`, pushing `now` on admit.

## Trade-offs
A sliding-window *log* (this approach) is exact but costs O(N) memory per active client; a sliding-window *counter* (weighted average of the previous and current fixed windows) is O(1) memory and good enough for most APIs, at the cost of being an approximation. Pick the log when correctness under adversarial traffic matters more than memory; the counter otherwise.

## Code
```python
import threading
import time
from collections import deque, defaultdict

class RateLimiter:
    def __init__(self, max_requests, window_seconds):
        self.max_requests = max_requests
        self.window = window_seconds
        self._locks = defaultdict(threading.Lock)
        self._log = defaultdict(deque)

    def allow(self, client_id):
        now = time.monotonic()
        with self._locks[client_id]:
            q = self._log[client_id]
            while q and q[0] <= now - self.window:
                q.popleft()
            if len(q) < self.max_requests:
                q.append(now)
                return True
            return False
```

## Solution
Per-client locks (rather than one global lock) mean clients don't contend with each other -- a burst from one client can't stall another's `allow()` call. The deque acts as the rolling log: trimming from the front before counting is what makes the window actually roll continuously rather than resetting at fixed boundaries, which is what prevents the classic fixed-window bug where a client sends N requests at `T-epsilon` and another N at `T+epsilon`, getting 2N through in a span smaller than T. The remaining gap is unbounded memory for clients that stop sending entirely -- a real system would need a periodic sweep to evict empty/stale per-client entries, e.g. an LRU with a TTL.
