## Question
Name and briefly explain the four pillars of object-oriented programming. Then: what is the "diamond problem" in multiple inheritance, and how do different languages avoid it?

## Hint
Three of the four pillars are about *hiding* something (data, complexity, implementation); the fourth is about *substituting* one thing for another. The diamond problem is purely a multiple-inheritance issue -- languages that only allow single inheritance from classes don't have it.

## Answer
**Encapsulation** (bundling data with the methods that operate on it, hiding internal state), **abstraction** (exposing only what a consumer needs, hiding implementation detail), **inheritance** (a class reusing/extending another's behavior), and **polymorphism** (the same interface behaving differently depending on the concrete type). The diamond problem arises when a class inherits from two classes that share a common ancestor -- it's ambiguous which ancestor's version of a shared method wins.

## Solution
**Encapsulation** means an object's internal state is only reachable through its own methods -- a `BankAccount` exposes `deposit()`/`withdraw()`, not a public `balance` field anyone can set directly, so invariants (balance never negative) stay enforceable in one place. **Abstraction** is the related but distinct idea of hiding *complexity*, not just *data* -- an abstract `Shape.area()` lets calling code work with shapes generically without knowing whether it's computing a circle's or a triangle's area. **Inheritance** lets a `Car` class reuse `Vehicle`'s fields and methods instead of duplicating them, expressing an "is-a" relationship. **Polymorphism** is what makes that reuse useful at call sites: a function that takes a `Vehicle` and calls `.drive()` works correctly whether it's handed a `Car` or a `Motorcycle`, without an `if/elif` chain checking the concrete type.

The **diamond problem**: if class `B` and class `C` both inherit from `A`, and class `D` inherits from both `B` and `C`, which version of a method `D` inherits if both `B` and `C` override something from `A`? The ambiguity is structural, not a corner case -- `D` has two paths back to `A`, forming a diamond shape in the inheritance graph.

Languages take genuinely different positions on this:
- **C++** allows it and makes you resolve it explicitly (`D::method` must disambiguate, or `A` must be inherited `virtual` so there's only one shared `A` sub-object instead of two).
- **Java and C#** sidestep it by disallowing multiple inheritance of *classes* entirely -- a class has exactly one superclass. They still allow implementing multiple *interfaces*, and Java's default interface methods reintroduced a narrower version of the same ambiguity, resolved by forcing the implementing class to override the method explicitly if two interfaces provide conflicting defaults.
- **Python** allows multiple inheritance and resolves it deterministically via the C3 linearization algorithm (the MRO, inspectable via `ClassName.__mro__`), which produces a single consistent method-resolution order rather than asking the programmer to disambiguate at each call site.

The general lesson: multiple inheritance of *behavior* (classes) is the risky kind; multiple inheritance of *contracts* (interfaces, with no shared implementation to conflict over) is what most modern languages allow freely instead.
