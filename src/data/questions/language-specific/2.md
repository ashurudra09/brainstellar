## Question
What is the Global Interpreter Lock (GIL) in CPython? Why does it exist, and what does it actually mean for multi-threaded Python code -- does threading ever help?

## Hint
The GIL protects one specific thing: CPython's own object reference counts. Think about what would happen to `refcount += 1` if two threads ran it at the same time without a lock.

## Answer
The GIL is a single global mutex that only lets one thread execute Python bytecode at a time, even on a multi-core machine. It exists because CPython's memory management (reference counting) isn't thread-safe without it. This means CPU-bound multi-threaded Python code doesn't get faster from more threads -- but I/O-bound code still benefits, because the GIL is released during blocking I/O.

## Solution
CPython tracks every object's lifetime with a reference count stored on the object itself. `x = y` increments a refcount; a variable going out of scope decrements one; hitting zero frees the object. That increment/decrement is not atomic -- without a lock, two threads mutating the same object's refcount simultaneously can lose an update, leaking memory, or worse, freeing an object that's still referenced (a use-after-free). The GIL is CPython's solution: rather than a fine-grained lock per object (which was tried, and was slower for the single-threaded case due to lock overhead), one global lock serializes *all* bytecode execution, refcounting included.

The practical consequence is a sharp split by workload:

- **CPU-bound** (tight number-crunching loops, image processing in pure Python): threads don't help, because only one can hold the GIL and execute bytecode at a time -- adding threads can even make it slower from lock-switching overhead. The real fix is `multiprocessing` (separate processes, separate GILs) or dropping into C/numpy/Cython for the hot loop, since those release the GIL while doing the actual work.
- **I/O-bound** (network calls, disk reads, `time.sleep`): threads help a lot, because CPython releases the GIL around blocking syscalls specifically so another thread can run while the first one waits. This is why `requests` in a thread pool scales fine, but a thread pool doing matrix multiplication in pure Python doesn't.

Two things worth knowing beyond the basics: `asyncio` sidesteps the GIL question entirely for I/O-bound work by using a single thread and cooperative scheduling instead of OS threads. And PEP 703 (accepted, landing as an opt-in build in recent CPython versions) is the project's answer to removing the GIL -- it replaces refcounting's thread-safety guarantee with per-object locking and biased reference counting instead of one global lock, which is a much bigger change than it sounds, since huge swaths of the C extension ecosystem have implicitly relied on the GIL for their own thread-safety for decades.
