## Question
How do `bisect_left` and `bisect_right` (from Python's `bisect` module) work internally, and what's the use case for each? When does the choice between them actually change the answer?

## Hint
Both do the same binary search when there are no duplicates of your target value in the array. They only diverge when the target already exists in the array -- ask yourself whether you want to land *before* or *after* that block of ties.

## Answer
For a sorted array `arr` and target `x`:
- `bisect_left(arr, x)` = index of the **first** element `>= x` (equivalently, count of elements strictly `< x`).
- `bisect_right(arr, x)` = index of the **first** element `> x` (equivalently, count of elements `<= x`).

Use `bisect_left` when a match on `x` itself should be treated as "not yet past it" (strict `<` boundary). Use `bisect_right` when a match on `x` should be included (`<=` boundary) -- e.g. finding the last index with value `<= x` is `bisect_right(arr, x) - 1`.

## Code
```python
from bisect import bisect_left, bisect_right

arr = [2, 4, 4, 4, 7]

bisect_left(arr, 4)   # 1  -- before the block of 4s
bisect_right(arr, 4)  # 4  -- after the block of 4s

# Count occurrences of a value in a sorted array
count_of_4 = bisect_right(arr, 4) - bisect_left(arr, 4)  # 3

# "Last index with value <= x" -- always bisect_right, minus 1
last_le_4 = bisect_right(arr, 4) - 1   # 3
last_lt_4 = bisect_left(arr, 4) - 1    # 0 (strict <)
```

## Solution
Both functions do the same binary search and would return the same index if you inserted `x` into `arr` -- they only disagree about *where* to insert it relative to existing equal elements. `bisect_left` inserts to the left of any ties (so `arr[:i]` are all `< x`), and `bisect_right` inserts to the right of any ties (so `arr[:i]` are all `<= x`). That's the entire difference, and it only matters when `x` is actually present in `arr`; on an array with no duplicates of `x`, both return the same index.

This shows up constantly in interval-scheduling problems (e.g. weighted interval scheduling / "Maximum Profit in Job Scheduling"): given jobs sorted by end time, you often need "the last job whose end time is `<= this job's start time`" (touching intervals are compatible). The correct one-liner is:

```python
j = bisect_right(end_times, start_time) - 1  # -1 sentinel if none exist
```

A common bug is reaching for `bisect_left` instead and manually patching the off-by-one with branches for the boundary cases. It looks like it works on inputs where the tie you care about happens to sit at index 0, but fails silently the moment a duplicate end-time exists elsewhere in the array: `bisect_left` lands on the *first* occurrence of a tie, so subtracting 1 skips over an interval that is actually still compatible (`end == start` is allowed) and just happens to share its end time with an earlier interval. Since DP tables built on top of this (`dp[i] = max(dp[i-1], score[i] + dp[j])`) are monotonically non-decreasing in `j`, silently returning a smaller-than-optimal `j` doesn't crash -- it just quietly returns a suboptimal answer, which is a much nastier class of bug to catch. `bisect_right - 1` sidesteps the whole problem in one line, with no branching.

The other standard use is `bisect.insort` (built on `bisect_left`/`bisect_right`) to insert into a sorted list while keeping it sorted -- `bisect_left`-based insertion puts new equal elements before existing ones, `bisect_right`-based (the default) puts them after, which matters if you're relying on insertion order to break ties among equal values.
