## Question
How does Python implement its built-in `dict`, and how does that compare to C++'s `std::map`? In particular: what's the underlying data structure of each, what's the time complexity of lookup/insert, and what ordering guarantees (if any) does each give you?

## Hint
Both are "associative arrays" from the outside, but one is built on hashing and the other on a balanced tree -- that single difference explains almost every observable behavior gap between them (ordering, worst-case complexity, iteration order).

## Answer
`dict` is a hash table: average O(1) lookup/insert, insertion-ordered iteration (guaranteed since Python 3.7), no ordering by key. `std::map` is a red-black tree: guaranteed O(log n) lookup/insert, iteration in sorted key order, always. If you want hash-table semantics in C++, that's `std::unordered_map` instead -- `std::map` is deliberately the ordered one.

## Code
```python
# Python: dict is hash-based, iterates in insertion order
d = {}
d['banana'] = 1
d['apple'] = 2
list(d.keys())  # ['banana', 'apple'] -- insertion order, not sorted
```
```cpp
// C++: std::map is a red-black tree, iterates in sorted key order
std::map<std::string, int> m;
m["banana"] = 1;
m["apple"] = 2;
// iterating m yields "apple" before "banana" -- sorted by key, always
```

## Solution
**Python's `dict`** is a hash table implemented as an open-addressing array of slots (not a bucket-of-linked-lists like Java's `HashMap`). Each key's hash determines a probe sequence into that array; a `PyDictKeyEntry` stores the hash, key, and value together, and since 3.6 CPython keeps a separate compact array of insertion-ordered entry indices alongside the hash table itself -- that's the implementation detail that makes insertion-order iteration both guaranteed *and* cheap. Average-case lookup/insert/delete is O(1); worst case (pathological hash collisions) degrades to O(n), which is why keys must be hashable and ideally have a well-distributed `__hash__`.

**C++'s `std::map`** is required by the standard to be a sorted associative container with O(log n) operations, and every mainstream implementation (libstdc++, libc++, MSVC STL) satisfies that with a self-balancing red-black tree. Each node holds a key-value pair plus left/right/parent pointers; the tree invariants guarantee O(log n) worst case for lookup, insert, and delete -- no pathological input can degrade it further, unlike a hash table. The cost is that every operation touches `O(log n)` nodes scattered across the heap (worse cache locality than a hash table's flat array), and you pay `log n` even when you don't need sorted iteration.

The practical takeaway: reach for `dict` (or `std::unordered_map`) when you want fast average-case lookup and don't care about order; reach for `std::map` (Python doesn't have a true tree-map in the standard library -- `sortedcontainers.SortedDict` is the closest equivalent) when you need guaranteed worst-case bounds or sorted iteration as a first-class feature, not an afterthought.
