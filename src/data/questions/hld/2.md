## Question
Design an API gateway that sits in front of dozens of backend services, enforcing per-API-key rate limits, at a scale of ~1M requests/sec across thousands of distinct keys.

## Requirements
- Rate-limit decisions must be consistent across many gateway instances (a key shouldn't get N times the limit by hitting N different gateway nodes).
- Limiting must add negligible latency to the request path.
- Gateway nodes can be added/removed freely (no sticky routing by key).
- Backends should never see traffic that exceeds a key's limit.

## Hint
The moment you have multiple stateless gateway nodes enforcing one shared per-key limit, you've turned a local counter problem into a distributed-counter problem.

## Approach
- Centralize the counter in a fast shared store (Redis) using an atomic increment-with-expiry (or a Lua script implementing a sliding-window counter) keyed by API key -- every gateway node checks/increments the same counter instead of keeping its own.
- Co-locate a Redis cluster per region close to the gateway nodes to keep the added hop cheap; each key's counter lives on one shard (consistent hashing), so the "many nodes, one counter" property holds without a global lock.
- On the hot path, the gateway does one round trip to Redis per request; on Redis unavailability, fail open with a conservative local fallback limit rather than failing every request.

## Trade-offs
A fully centralized counter is exactly correct but adds a network hop to every single request; an alternative is giving each gateway node a *local* token-bucket that's a fraction of the global limit (limit / node_count), trading strict accuracy (a burst that happens to land on one node exhausts its share early) for zero added latency. Centralize when correctness under bursty, adversarial traffic matters (e.g. a paid-tier limit that's part of a contract); shard the budget locally when the limit is a soft protection mechanism and approximate fairness is fine.

## Solution
The core tension is that rate limiting is inherently a shared-state problem, but the gateway layer wants to be stateless for elastic scaling -- so the shared state has to live somewhere else, and that somewhere needs to be fast enough not to dominate request latency at 1M req/sec. Putting it in Redis (or an equivalent in-memory store) with atomic operations resolves the consistency requirement; regional co-location and a local fail-open fallback are what keep that centralization from becoming either a latency problem or a single point of failure.
