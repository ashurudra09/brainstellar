# v2.1 — Build speed, Language-Specific domain, Cheatsheets

Three independent tracks plus a documentation pass. Phase A (build speed)
touches config and `gatsby-node.js`; Phase B (one new domain, plus
folding OOP into LLD) is almost pure data; Phase C (cheatsheets) adds a
new content collection. A, B and C can land in any order, but A first
makes B and C faster to iterate on. **Phase D (README) runs last**, since
it documents whatever A, B and C actually settled on.

**Decisions taken during review:**

- The legacy per-question alias routes (`/puzzles/{category}/{qid}` and
  `/puzzles/{difficulty}/{qid}`) are **deleted outright**, not
  redirected. Speed wins, and it makes quant's routing look like every
  other domain's.
- **OOP is not a separate domain.** It folds into `lld`, which already
  declares an `oop-principles` category for exactly this.

## Measured baseline

Two `gatsby build` runs on this machine (Windows, 12 logical cores), the
second with a warm `.cache`. Measured at `f928e5e`; the three UI commits
since (`d46dcea`..`8c6380c` — nav contrast, the `QuestionFilters`
toolbar, dropping `DomainCards`) touch only components and `layout.css`,
create no pages, and leave every number below intact.

| Stage | Cold | Warm |
|---|---|---|
| bootstrap | 12.0s | ~6s |
| Building production JS/CSS bundles | 37.5s | 8.7s |
| Building HTML renderer | 18.4s | 1.9s |
| run queries in workers (811) | 4.6s | 0.4s |
| **gatsby-plugin-sharp IMAGE_PROCESSING** | **61.3s** (11 jobs) | **11.6s** (2 jobs) |
| **Building static HTML (837 pages)** | **29.0s** | **21.7s** |
| **stitching slices** | **24.0s** | **15.5s** |
| **Total** | **131.0s** | **64.6s** |

Two things dominate:

1. **sharp**, 61s cold / 12s warm — for **11 small PNG/SVG diagrams**.
   CI is always cold, so CI pays the full 61s plus the cost of installing
   sharp's native binary.
2. **Page count**, 837 pages — static HTML + slice stitching are both
   linear in it and together are 53s cold / 37s warm (**58% of the warm
   build**). Note that HTML for *all* 837 pages is rebuilt even when
   nothing changed, because the webpack bundle hash changes on every run
   and invalidates every page.

|---|---|
| `/q/{domain}/{qid}` — canonical | 130 |
| `/q/{domain}` — domain lists | 9 |

## Phase A — Build speed

### A1. Delete both per-question alias route families  *(biggest single win)*

**837 → 267 pages (−68%).** In `gatsby-node.js`, delete from the
`puzzles.forEach` block:

- the whole `difficulties.forEach` loop (456 pages),
- the `puzzles/${category}/${qid}` `createPage` call (114 pages).

What survives is `/puzzles/{qid}` — quant's real canonical URL — plus the
`/puzzles/{category}` and `/puzzles/{difficulty}` **list** pages and the
`/puzzles` album grid, which are navigation, not aliases.

No redirects. They were only worth considering to preserve SEO that
belongs to upstream brainstellar.com rather than to this fork, and
GitHub Pages ignores `_redirects` anyway.

Falls out of the deletion for free:

- `previousCategoryPuzzleId` / `nextCategoryPuzzleId` /
  `previousDifficultyPuzzleId` / `nextDifficultyPuzzleId` — four
  `find`/`slice().reverse().find()` scans per puzzle, now dead.
- The `category` and `difficulty` `pageContext` fields, and with them the
  two conditional `<h2>{category} puzzles</h2>` / `<h2>{difficulty}
  puzzles</h2>` headings at the top of `src/templates/question.js`. Those
  headings only ever rendered on the alias pages.
- `const categories = ...` / `const difficulties = ...` stay, but only to
  feed the list pages.

Est. saving: **~25s warm, ~36s cold**, plus 570 fewer `page-data.json`
files written and stale-checked on every single build.

### A2. Drop sharp entirely  *(biggest cold/CI win)*

All 11 images are small static diagrams (`maxWidth: 200`, `quality: 100`,
`withWebp: false`) — the responsive-image machinery is generating a srcset
ladder and a blur-up placeholder for images that are already smaller than
one ladder rung.

- Remove `gatsby-remark-images`, `gatsby-plugin-sharp`,
  `gatsby-transformer-sharp`, `gatsby-plugin-image` from
  `gatsby-config.js` and `package.json`.
- `gatsby-remark-copy-linked-files` is **already** in the remark plugin
  list and already does the only job that remains: copy the file into
  `public/static/` and rewrite the `src`.
- Add `.content-text img { max-width: 100%; height: auto; }` to
  `layout.css` to replace the width cap `gatsby-remark-images` provided.
  There is no global `img` rule today — the only three are scoped to
  `.nav` and `.btn-scalegrey` — so this adds behaviour rather than
  fighting an existing rule.
- Est. saving: **~61s cold, ~12s warm**, plus a much faster `npm install`
  in CI (sharp is by far the heaviest dependency in the tree).
- Verify afterwards on the questions that actually have images, e.g.
  `/puzzles/1035` and any `.drawio.svg` ones — the `.drawio.png`/
  `.drawio.svg` webpack `file-loader` rules in `onCreateWebpackConfig` are
  a separate path and stay as they are.

### A3. Get `cheerio` and `he` out of the client bundle

`src/templates/question.js:13` does a module-scope `require('cheerio')`
purely so `Head` can strip tags for the meta description. Gatsby's `Head`
API also runs in the browser on client-side navigation, so cheerio — a
full HTML parser — is compiled into the browser bundle for every question
page. It is also the sole reason for the `node:sqlite` webpack `externals`
workaround at the bottom of `gatsby-node.js`.

- Replace with the tag-strip regex `splitSections` already uses
  (`html.replace(/<[^>]*>/g, ' ')`) plus a small entity map for the five
  named entities remark emits, or — cleaner — compute the description once
  in `gatsby-node.js` and pass it through `pageContext`.
- Drop `cheerio` and `he` from `package.json`, and delete the `externals`
  block that only existed to work around cheerio's `undici` dependency.
- Est. saving: a few seconds off the 37.5s browser bundle and the 18.4s
  HTML-renderer compile, and a meaningfully smaller runtime bundle for
  every question page.

### A4. Refresh browserslist

The build warns that `caniuse-lite` is 15 months stale, which makes Babel
target older browsers than intended — more transpilation, larger output.

```bash
npx update-browserslist-db@latest
```

### A5. Fix CI (`.github/workflows`)

Currently: `actions/checkout@v2`, Node 18, `npm install`, no caching, so
every push pays a full cold build **plus** a full dependency resolve.

- `actions/checkout@v4`, `actions/setup-node@v4` with `node-version: 20`
  and `cache: 'npm'`; `npm ci` instead of `npm install`.
- Add `actions/cache` for `.cache` and `public`, keyed on the lockfile +
  a hash of `src/data/**`, so Gatsby's incremental build works in CI —
  this is what turns the CI build from the 131s column into the 65s
  column, and A1+A2 then take it well below that.

### A6. Optional — finish the alignment  *(needs a yes; see open decisions)*

A1 makes quant's *question* routes match every other domain's in count,
but quant is still the only domain with a bespoke URL shape.
`src/templates/question.js:41` and `QuestionTable.js:9` both carry a
`domain === 'quant' ? '/puzzles/{qid}' : '/q/quant/{qid}'` special-case,
and `/q/quant/{qid}` is built *alongside* `/puzzles/{qid}` today — 114
pages rendering the same question twice.

Note that the hub already prefers the aligned shape: since the
`progress-tile-link` change, `ProgressStats.js:88` links every domain
tile — quant included — to `/q/{slug}`. So `/q/quant` is already the
domain page users land on, and only the per-question URL is still
special-cased.

Collapsing quant onto `/q/quant/{qid}` deletes those 114 duplicates and
both special-cases. Going further and dropping the `/puzzles` album grid,
`legacy-list.js` and the 8 list pages takes the site to **~144 pages** and
removes two templates outright.

That last step is genuinely lossy — `/puzzles` is an illustrated landing
page, not an alias — so it is a separate yes/no, not part of A1.

### Expected result

With A1–A5: cold ≈ **131s → ~40s**, warm ≈ **65s → ~22s**.
With A6 as well: warm ≈ **~17s**.

### Explicitly not doing

- Splitting the site into multiple Gatsby builds, adding a bundler swap,
  or moving off Gatsby. The two fixes above are 90% of the available win
  for a fraction of the risk.
- `GATSBY_CPU_COUNT` — Gatsby 5 no longer reads it.
- Chasing the `'WMIC' is not recognized` warning. It is emitted twice
  during the webpack stage and comes from outside `node_modules`; it is
  cosmetic and does not gate the worker pool.

## Phase B — Language-Specific domain, OOP into LLD

Mostly a data edit, since Phase 1 of v2 already made `src/data/domains.js`
the single source of truth.

### B1. `src/data/domains.js` — one new entry

```js
{
  slug: 'language-specific',
  label: 'Language-Specific',
  icon: '🔤',
  accent: '#4aa8a0',
  difficulties: ['easy', 'medium', 'hard'],
  categories: ['python', 'cpp', 'java', 'javascript', 'go', 'comparative'],
  sections: { open: ['Question'], collapsed: ['Hint', 'Answer', 'Code', 'Solution'] },
},
```

The categories are the languages themselves, plus `comparative` for
exactly the example that prompted this domain ("how does Python implement
`dict`, compared to C++'s `map`") — a question about two languages at
once, which belongs under neither one alone.

The domain slug stays `language-specific` even though the label reads
"Language-Specific"; the slug is the URL (`/q/language-specific`) and the
folder name.

### B2. Fold OOP into LLD

`lld` already declares an `oop-principles` category, so this is a
labelling and routing change, not a schema one:

- `label: 'LLD'` → `label: 'LLD & OOP'`, so the domain card, the header
  `<select>` and the `/all` filter chip all say what the domain actually
  holds. Nothing keys off the label — `slug` stays `lld`, so no URLs,
  folders, or `progress.json` keys move.
- Categories stay as they are: `['design-patterns', 'oop-principles',
  'concurrency', 'api-design', 'case-study']`. `oop-principles` is a
  perfectly good bucket for concept questions today. If it later fills up
  enough that filtering by it stops being useful, split it then into
  `solid` / `inheritance-polymorphism` / `abstraction-encapsulation` —
  that is a cheap edit later and speculative now.
- `sections` stay as they are. A pure OOP concept question simply omits
  the `Requirements` section; the renderer only renders sections that are
  present, so a declared-but-absent section costs nothing.

The routing rule to write down (it is the only thing that could drift):
**a question that asks you to *design* something goes to
`case-study`/`design-patterns`; a question that asks you to *explain* an
OOP idea goes to `oop-principles`.** Both are `lld`.

### B3. Content folder and seeds

`mkdir src/data/questions/language-specific`, then two seed questions
matching Phase 7's precedent:

- the `dict`-vs-`std::map` question from the request (hard,
  `comparative`),
- one on Python's GIL or C++ move semantics (medium, `python` / `cpp`).

qids start at 1, via
`node .claude/skills/add-question/scripts/next_question_id.js --domain language-specific`.

Optionally add one `lld` / `oop-principles` seed too, since that category
currently has no example to pattern-match against — the two existing
`lld` questions are `design-patterns` and `concurrency`.

### B4. Update the authoring skill

`.claude/skills/add-question/SKILL.md`:

- Frontmatter `description`: "nine domains" → "ten domains"; add
  `Language-Specific` to the parenthesised list and change `LLD` to
  `LLD & OOP` (this string is what triggers the skill, so an OOP question
  described as such needs to find a match in it).
- Step 2's domain-inference list: add "a question about how a specific
  language implements something, or a cross-language comparison →
  `language-specific`", and extend the `lld` line to "an
  object-design/design-patterns question, **or an OOP concept question**
  → `lld`".
- Add the two tie-breaks explicitly, since they are the only ambiguous
  calls this change introduces:
  - **Names a language → `language-specific`**, even when the topic is
    OOP. "How does Python's MRO resolve diamond inheritance?" is
    `language-specific`/`python`; "what is the diamond problem?" is
    `lld`/`oop-principles`.
  - **Explain vs design** within `lld` — the B2 rule, which picks the
    *category*, not the domain.
- Mirror to the parent workspace copy per the skill's own step 7
  (`diff -r .claude/skills/add-question ../.claude/skills/add-question`).

`gatsby develop`, then check `/q/language-specific`, the domain

## Phase C — Cheatsheets

### The design question

Claude publishes artifacts in two formats, and cheatsheets show up as
both:

- **HTML** — a self-contained page with its own `<style>` block, its own
  palette and fonts, and sometimes its own `<script>` driving tabs,
  filters, collapsibles or a search box.
- **Markdown** — a plain document, no styling of its own.

"Merging their UIs" means the artifact's *content and layout* survive but
its *chrome* is replaced by the site's — so cheatsheets sit inside
`Layout`, respect the site's light/dark theme, and use the site's type
scale. For a Markdown artifact that is nearly free. For an HTML one it is
the whole job, and it is what C4 step 3 specifies.

Rejected: iframing the artifact (no theme, no nav, no search, a scrollbar
inside a scrollbar) and committing raw artifact HTML verbatim (every
cheatsheet ships its own conflicting stylesheet).

Chosen: **each cheatsheet is a markdown file** in
`src/data/cheatsheets/`, rendered through the remark pipeline that already
exists (KaTeX and Prism come free), inside the normal `Layout`. Where a
cheatsheet genuinely needs visual layout — a comparison grid, colour-coded
cards, pill badges — the markdown embeds raw HTML using a **small shared
class vocabulary** defined once in CSS against the site's existing
variables. That vocabulary is what makes "merge the UIs" a deterministic
instruction the skill can follow instead of a judgement call.

### C1. Source the new collection

`gatsby-config.js`: second `gatsby-source-filesystem` entry,
`name: 'cheatsheets'`, `path: ${__dirname}/src/data/cheatsheets`.

`gatsby-node.js` `onCreateNode` currently sets
`fields.domain = parent.relativeDirectory` for *every* `MarkdownRemark`
node. Add `fields.collection = parent.sourceInstanceName` and only set
`domain` when the collection is `questions`.

Then three queries need a `collection: { eq: "questions" }` filter so
cheatsheets do not leak into question lists:

- `gatsby-node.js` `createPages`
- `src/pages/index.js`
- `src/pages/all.js`

(`albums.js`, `domain.js` and `legacy-list.js` already filter on
`fields.domain`, so they are safe.)

### C2. The shared class vocabulary — `src/components/cheatsheet.css`

Roughly eight classes, all built on the existing `--color-text`,
`--color-background-off`, `--qf-border` and `--difficulty-*` variables so
they theme themselves:

`.cs-grid` (responsive card grid) · `.cs-card` · `.cs-card h4` ·
`.cs-pill` (inline badge, `--accent`) · `.cs-cols` (2-up comparison) ·
`.cs-callout` (note/warning) · `.cs-kbd` · `.cs-table` (the existing
`.puzzle-table` look, reused).

**Copy these off what the recent UI work already established rather than
inventing a parallel look** — that is most of the "merged UI" requirement,
and it is free:

- `.cs-grid` / `.cs-card` → `.progress-tiles` / `.progress-tile`
  (`layout.css:1048`): `display: flex; flex-wrap: wrap` (deliberately not
  grid — the Stage 3 fix was specifically so an incomplete last row
  centres), `--color-background-off`, `border-radius: 8px`, a 4px
  `--accent` top border.
- `.cs-pill` → `.filter-chip` (`layout.css:1140`) and
  `.pt-difficulty-badge` (`layout.css:1453`), both already `--accent`-driven.
- Borders → `--qf-border`, the token the filter toolbar introduced, rather
  than a new one.

This file is the contract between the skill and the site. Keeping it
small is the point: a cheatsheet that needs a ninth class is a signal to
generalise, not to inline a `<style>` block.

### C3. Pages

- `src/templates/cheatsheet.js` — `Layout` + `Seo` + the rendered HTML +
  a back-link to `/cheatsheets`. Roughly 40 lines; much simpler than
  `question.js` since there is no section splitting, no progress tracking,
  no prev/next.
- `src/pages/cheatsheets.js` — index page, `.cs-grid` of cards from an
  `allMarkdownRemark` query filtered to the `cheatsheets` collection,
  showing icon, title, summary and tags. Handles the empty state.
- `gatsby-node.js` — create `/cheatsheets/{slug}` per node inside the
  existing `createPages`.
- `src/components/header.js` — a `Cheatsheets` nav link next to
  `All Questions`.

Frontmatter: `title`, `slug`, `summary`, `icon`, `tags: [...]`,
`updated`. No `qid`, no difficulty, no progress tracking — cheatsheets are
reference material, not practice items, and keeping them out of
`progress.json` keeps the v2 progress schema untouched.

### C4. `/add-cheatsheet` skill

`.claude/skills/add-cheatsheet/SKILL.md`, structured like `add-question`
(which is a good template — it already handles the site-root discovery and
the no-heredocs trap, both of which apply identically here).

Steps it will specify:

1. **Locate the site root** — same `find` incantation as `add-question`;
   and the same rule that content goes through the Write tool, never a
   heredoc.
2. **Find the cheatsheet.** In priority order: an artifact published
   earlier in this conversation; an artifact URL the user pasted (read it
   back with the Artifact tool's `read` action); or content pasted
   directly into the invocation. Stop and ask rather than inventing one.
   Read the whole artifact before converting it — a cheatsheet's value is
   in its long tail of rows, and a partial read silently drops them.
3. **Detect the format, then convert.** The artifact is either HTML or
   Markdown, and the skill branches on that first.

   **Markdown artifact** — the easy case. Copy the body through
   essentially unchanged; the site's remark pipeline already renders
   headings, tables, fenced code and `$...$` math. The only work is
   demoting a leading `#` title into frontmatter (so it is not printed
   twice above the template's own heading) and adding the C3 frontmatter.

   **HTML artifact** — convert, don't transplant. Discard the artifact's
   `<style>`, its fonts, its colours, its `<script>`, and the wrapper
   divs that only exist to centre the page. Then map what remains:

   | In the artifact | Becomes |
   |---|---|
   | `<h1>` | frontmatter `title` |
   | `<h2>`/`<h3>` | `##` / `###` |
   | `<table>` | markdown table |
   | `<pre><code>` | fenced block with a language tag |
   | `<ul>`/`<ol>` | markdown lists |
   | KaTeX/MathML output | `$...$` / `$$...$$` |
   | card / tile grid | `<div class="cs-grid">` + `.cs-card` |
   | two-column comparison | `.cs-cols` |
   | coloured badge, chip, tag | `.cs-pill` |
   | note / warning / tip box | `.cs-callout` |
   | `<kbd>`, shortcut key | `.cs-kbd` |

   Prefer plain markdown wherever it carries the same meaning — reach for
   a `.cs-*` class only when the layout itself is load-bearing (a
   side-by-side comparison, a scannable grid). Never emit a hardcoded
   colour, an inline `style=`, or a `<style>` block; anything that seems
   to need one is a note to the user in step 6, not an inline exception.

   **If the HTML artifact is interactive** — tabs, filters, collapsibles,
   a live search box — that behaviour cannot survive the conversion, and
   pretending otherwise produces a cheatsheet with dead buttons on it.
   Flatten it instead: tabs become sequential `##` sections, collapsibles
   are expanded inline, a filterable table becomes the full table (the
   page is `Ctrl-F`-able anyway). Then **say so explicitly in step 6** —
   name what was interactive and what it flattened into, so the user can
   decide whether that particular cheatsheet wants different treatment.
   Do not port the `<script>`; a per-cheatsheet script is exactly the
   per-cheatsheet stylesheet problem in a second form.
4. **Choose the slug** — kebab-case from the title, and check
   `src/data/cheatsheets/` for a collision. A collision means the user is
   updating an existing cheatsheet: confirm, then overwrite and bump
   `updated`, rather than silently creating `foo-2`.
5. **Write** `src/data/cheatsheets/{slug}.md` with the C3 frontmatter.
   Images from the artifact go alongside it as `{slug}-{n}.{ext}`.
6. **Report back** — slug, title, tags, the file written, and the local
   URL `/cheatsheets/{slug}` to check it in `gatsby develop`. Name the
   source format (HTML or Markdown), anything interactive that got
   flattened, and anything the class vocabulary could not express. Do not
   commit; the user reviews first.
7. **Mirror the skill** to the parent workspace `.claude/skills/`, same as
   `add-question` step 7.

### C5. Verify

Run `/add-cheatsheet` end to end against **two** real artifacts — one
Markdown, one HTML with styling — since step 3's two branches barely
share any code path and only exercising one of them proves half the
skill. Eyeball `/cheatsheets/{slug}` in both light and dark mode; the
HTML one is where a leaked colour will show up. Confirm neither
cheatsheet appears on `/all`, on `/`, or in the counts in
`ProgressStats` — that is the one thing C1's filters can silently get
wrong.

## Phase D — Documentation

Runs **last**, after A, B and C have landed — a README written against
the plan rather than against the finished repo is just a second thing to
keep in sync.

### D0. What "since the fork" means

The last upstream commit is `fcfeac8` (2025-06-29). Everything from
`f6170dd` (2026-08-28) onward is this fork. The README has not been
touched since — it still describes the upstream quant-puzzles site with a
short practice-tracker section bolted on.

### D1. Fix what is actively wrong first

These are not omissions, they are statements that no longer hold, and
they are the parts most likely to waste someone's time:

- **"writes `src/data/puzzles/{id}.md`"** — that directory does not
  exist. It is `src/data/questions/{domain}/{qid}.md`.
- **"assigns the next `puzzleId`"** — the field is `qid`, and ids are
  scoped per domain (`quant:1` and `dsa:1` are different questions).
- **The "Adding a puzzle" section points at
  `.claude/skills/add-puzzle/SKILL.md`**, which is now a four-line alias
  that forwards to `add-question`. Point at the real skill.
- **The header still reads "Quantitative Aptitude Puzzles"** — the site
  covers ten domains now.
- **The sharp/Node-20 warning** is the single most load-bearing paragraph
  in the file, and A2 deletes the dependency it warns about. Once sharp
  is gone the Node constraint relaxes; re-check what the floor actually
  is before rewriting the paragraph rather than assuming it disappears.

### D2. Document what was added

Nothing below is in the README today. Grouped as sections, roughly in the
order a new reader needs them:

- **What this is** — a personal placement-prep dashboard forked from
  brainstellar.com, not a puzzles site. One paragraph, and it replaces
  the current opening.
- **Domains** — the ten of them, that `src/data/domains.js` is the single
  source of truth for slugs/categories/difficulties/section layout, and
  that adding a domain is a one-file edit plus a folder.
- **Routes** — `/` dashboard, `/all`, `/q/{domain}`,
  `/q/{domain}/{qid}`, `/cheatsheets`. Whatever survives A1/A6 of the
  legacy `/puzzles` routes gets a one-line note; if A6's third rung is
  taken, they are simply gone and the README should not mention them.
- **Progress tracking** — solved / starred / revisit / notes, the
  spaced-repetition review queue and its default `[7, 14, 30, 60]` day
  intervals, `progress.json` at the repo root, and the fact that it is
  **gitignored** (so it is per-machine, and there is no sync). Worth
  stating explicitly that progress persists through the dev-only
  `/__progress` endpoints under `gatsby develop` and falls back to
  `localStorage` under `gatsby build`/`serve` — that difference is
  surprising and undocumented.

## Open decisions

1. **How far to take the alignment (A6).** A1 leaves quant still
   special-cased: `/puzzles/{qid}` and `/q/quant/{qid}` both build, for
   the same 114 questions, and two files carry a
   `domain === 'quant' ? ... : ...` branch to decide which one to link
   to. Three rungs, pick one:
   - **Stop at A1.** 267 pages. Quant keeps its pretty URLs; the
     special-case stays.
   - **Collapse quant onto `/q/quant/{qid}`.** ~153 pages, and both
     special-cases disappear. Old `/puzzles/{qid}` links break.

     ~144 pages, two templates deleted, quant is indistinguishable from
     every other domain. Costs the illustrated album grid — `/q/quant`'s
     filter chips cover the same ground functionally, but it is a real
     page with real design in it, so this one is a judgement call rather
     than a cleanup.

2. **Cheatsheet fidelity (Phase C)** — the markdown-plus-shared-classes
   approach deliberately trades pixel fidelity to the original artifact
   for consistency with the site. If a particular cheatsheet's *visual
   design* is the point rather than its content, that one wants a
   different treatment. The sharper version of this: an HTML artifact
   whose interactivity is genuinely the feature — a filterable reference
   table, a decision-tree walkthrough — flattens into something duller
   than the original. If that turns out to be common rather than rare,
   the answer is a fourth `.cs-*` primitive or two (a `<details>`-based
   collapsible needs no JS at all, and a client-side table filter is one
   small shared component), not a `<script>` tag per cheatsheet. Worth
   revisiting once there are five or six real cheatsheets to look at
   rather than designing for it now.
